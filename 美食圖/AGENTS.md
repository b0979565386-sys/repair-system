# 公司附近午餐美食圖｜專案規則

本資料夾是「公司附近午餐美食圖」專案。開始任何工作前，先讀 `需求筆記.txt`。
本檔案的規則只適用於這個資料夾；儲存庫根目錄的 `AGENTS.md` 屬於報修登記系統，`聚餐餐廳登記/AGENTS.md` 屬於聚餐餐廳專案。

## 每次開工

1. 先把工作區更新到 GitHub 上最新的 `main`，再開始修改。
2. 確認目前分支與 `main` 沒有衝突；有衝突就先處理，不要在舊版本上繼續做。

## 金鑰與機密

- 只能使用 Supabase 的 **publishable key**（以 `sb_publishable_` 開頭）。
- **secret key 不可以寫進任何檔案**，包含程式碼、設定檔、說明文件、範例、測試與 commit 訊息。`service_role` 金鑰、資料庫密碼、個人存取權杖也一樣。
- 若地圖服務需要金鑰，只能使用可公開、並已限制網域的瀏覽器金鑰；優先選擇不需要金鑰的服務。
- 不要把金鑰貼在 Pull Request、Issue 或留言裡。
- 若發現 secret key 已經被提交，立刻停止工作並通知負責人更換金鑰；只刪除檔案不夠，因為它還留在 Git 歷史裡。

## 登入與權限

- 所有資料都必須登入才能讀取與寫入；未登入的 `anon` 角色不給任何資料表權限。
- 資料表必須啟用資料列安全（RLS）。新增店家與評價時，新增者／評分者欄位必須等於 `auth.uid()`。
- 一位同事對同一家店只能有一筆評價，要用資料庫的唯一限制保證，不能只靠網頁檢查。
- 提醒負責人在 Supabase 限制自行註冊，否則任何人都能註冊後讀取資料。
- 畫面上不顯示同事的 Email。

## 資料與隱私

- 所有店名、地址、座標、人名、帳號都使用虛構資料。
- 不放真實姓名、電話、Email，也不放客戶或廠商的真實資料。
- 範例座標使用虛構地點，不要標出真實店家或真實公司位置。

## 檔案與命名

- 這個專案的檔案都放在 `美食圖/` 資料夾內；Supabase 建表 SQL 放在 `美食圖/supabase/`。
- 使用者看得到的文字使用繁體中文。
- 欄位名稱在需求筆記、Excel、資料表與程式中要保持一致。
- 需求筆記沒寫到的地方標示「待確認」，不要自行假設。

## 完成後

1. 自行檢查成果：Excel 重新開啟確認工作表與資料；SQL 確認語法正確；網頁在手機尺寸測試主要流程。
2. 用 GitHub 外掛建立 Pull Request，標題使用繁體中文，說明變更內容與驗證方式。
3. 用 GitHub 外掛把 Pull Request 合併進 `main`。
4. 回報 Pull Request 連結與合併結果。

## 範圍

- 目前只做需求筆記列出的交付物：網頁美食圖、Supabase 資料表與存取規則、Excel 欄位表與範例資料。
- 未經確認不要在 Supabase 執行 SQL 或更改認證設定；交付的是檔案，由負責人自行執行。
- 「還沒決定的事」確認之前，相關功能先採最保守的做法，並在回報中說明。
